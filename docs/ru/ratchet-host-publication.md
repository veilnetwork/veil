# Долговечная публикация ratchet, состояние которого хранит приложение

Встроенный узел держит состояние ratchet в памяти. Приложение, сохраняющее
снимки, должно также резервировать исключительные позиции отправки **до**
публикации шифротекста. Одной проверки на стороне приложения недостаточно:
команды IPC могут позже одновременно израсходовать ключи, хотя несколько
команд перед этим увидели одну и ту же оставшуюся позицию.

До передачи прикладного трафика приложение вызывает `veil_ratchet_host_begin`.
Это создаёт локальное для процесса поколение подключения и сбрасывает старые
разрешения в памяти. Хранилище, к которому приложение никогда не подключалось,
сохраняет поведение без дисковой персистентности; вызов API не заменяет
долговечное хранилище.

Для каждой активной цепочки отправки приложение коммитит невключительную
верхнюю границу разрешённых позиций в своё зашифрованное хранилище. Только
после коммита и попытки обновить защитный якорь отката оно вызывает
`veil_ratchet_host_allow`. Нативное хранилище проверяет цепочку, позицию и
поколение подключения под тем же замком, который защищает расход ключа.
Разрешение нельзя перенести на другую цепочку; его размер ограничен
существующим пределом пропуска при восстановлении. Сами разрешения в снимки
не экспортируются.

Когда новый обмен PQXDH создаёт цепочку, её начальный шифротекст остаётся
неопубликованным. Через `veil_ratchet_host_state` приложение видит ограниченный
запрос на резервирование, сохраняет резерв новой цепочки, и исходная команда
повторяется. Сохранённый пролог позволяет первому опубликованному кадру
пропустить начальный неопубликованный индекс. Повторные заблокированные
попытки не расходуют дополнительные ключи.

Обработчик IPC ожидает разрешённую границу локально, в пределах существующего
дедлайна управляющей команды либо ограниченного ожидания обычной отправки.
Исчерпание резерва, закрытое подключение и вытесненный владелец не приводят к
обходу через открытый текст или шифрование без состояния. Локальная ошибка
отправки `RATCHET_NOT_DURABLE` (13) оставляет повтор приложению. Граница,
прикладной приоритет, категория медиа и поколение подключения не передаются
реле; формат сети и поведение mailbox не меняются.

При остановке приложение завершает своё подключение до последнего снимка и
дожидается начатых записей резервов до закрытия хранилища. Старое поколение
не может закрыть или авторизовать преемника. FFI отдельно сообщает о
вытесненном поколении: прежний обработчик не должен сохранять состояние
ratchet нового владельца в старый контейнер.

Восстановление остаётся задачей приложения: загрузить снимки, пропустить все
позиции ниже закоммиченных исключительных границ и только затем возобновить
отправку. Защита от отката всего контейнера зависит от политики якоря отката
приложения. Барьер публикации препятствует одновременному расходу сверх
сохранённой границы, но сам по себе не обнаруживает восстановление старого
контейнера.

Регрессионные проверки включают настоящий криптографический сценарий
сбоя/отката, параллельный допуск отправок, новые цепочки и сохранённые прологи,
ротацию DH, устаревших владельцев, границы резервов, ожидание в direct/relay IPC
и проверку буферов FFI.
